PART II: SECTION 5 REFLECTION QUESTIONS (ANSWERS 1 - 7)
--------------------------------------------------------------------------------

Question 1:
Why is it useful to specify action preconditions and effects before asking an LLM
to write the planner?
Answer:
Specifying preconditions and effects transforms an ambiguous natural-language concept
("move a package") into a formal mathematical contract. LLMs excel at syntax and
boilerplate generation when given crisp formal specifications, but frequently hallucinate
domain semantics when prompts are vague. Providing the explicit STRIPS schema
(preconditions, add-list, delete-list) establishes an exact ground truth that constrains
the LLM's code generation, ensuring that state transitions and applicability logic
mirror the physical problem faithfully.

Question 2:
Give an example of an error that could occur if the planner failed to check an
action's preconditions.
Answer:
If precondition checking is omitted, the robot could execute `Drop(Package, C)` in
the very first step while still at location A and without ever picking up the package.
Because the effect of Drop is `At(Package, C)`, the planner's state would immediately
record the package at C and conclude that the goal is achieved in 1 step! In the real
physical world, this would cause catastrophic failure: the robot would open an empty
gripper at waypoint A, leaving the package stranded while the software believes the
delivery is complete.

Question 3:
Why is a plan that "looks reasonable" not necessarily a valid plan?
Answer:
A plan can seem superficially plausible because the actions sound sensible in everyday
human language (e.g., "Move to C and drop package"). However, formal validity requires
unbroken causal soundness: at every single step k, every single precondition of action
a_k must be strictly entailed by the current world state S_{k-1}. Subtle physical
constraints—such as a missing hallway between two non-adjacent rooms (A and C),
exceeding robot carrying capacity, or failing to grasp an item before transit—are easily
overlooked by superficial human or LLM intuition, rendering the plan impossible in practice.

Question 4:
What did the LLM contribute to the implementation?

The LLM contributed rapid software synthesis:

Question 5:
What did you have to verify independently?
Answer:
Independent verification was required for:
1. Semantic correctness of state transitions: ensuring negative effects are subtracted
   before positive effects are added, avoiding proposition duplication.
2. Topological integrity: ensuring the robot only moves between physically adjacent nodes
   (A <-> B <-> C), rejecting non-existent corridors like (A -> C).
3. Goal evaluation logic: verifying that the goal condition strictly checks package
   placement rather than robot location.
4. Empirical behavior under edge cases: verifying that an impossible problem (Test B)
   actually reports failure rather than fabricating an imaginary path.

Question 6:
In this laboratory, where is logical reasoning being used?
Answer:
Logical reasoning is utilized at three key levels:
1. Within the Python agent: verifying precondition entailment (S |= Preconditions(a))
   and computing successor states through formal set subtraction and union.
2. Goal satisfaction testing: evaluating whether the final state entails the goal
   propositions (S_n |= G).
3. Within the Prolog verifier: using backward chaining (SLD resolution) over Horn clauses
   to formally prove whether candidate actions and paths follow from ground topological facts.

Question 7:
How is planning related to the search algorithms studied in the previous module?
Answer:
Planning is an application of state-space graph search. In traditional graph search
(e.g., BFS, DFS, A* on a maze), nodes are coordinates and edges are explicit graph links.
In planning, the state space is implicitly defined: nodes are sets of logical propositions
(world states), and edges are actions whose availability is dynamically generated by
evaluating logical preconditions. BFS operates identically across both: exploring states
level-by-level to guarantee the shortest path to a goal node.


PART III: SECTION 7.2 PROLOG REFLECTION QUESTIONS (ANSWERS 1 - 4)
--------------------------------------------------------------------------------

Question 1:
What is the difference between a Prolog fact and a Prolog rule?
Answer:
A fact is an unconditional, ground logical assertion in the knowledge base stating
that a relationship holds unconditionally (e.g., `connected(a, b).`).
A rule is a conditional statement (a Horn clause with a non-empty body) asserting
that a conclusion (head) is true provided that all conditions (body) are satisfied
(e.g., `can_move(X, Y) :- connected(X, Y).`). A fact can be viewed as a degenerate rule
whose body is unconditionally true.

Question 2:
How does a Prolog query correspond to asking whether something follows from a
knowledge base?
Answer:
A Prolog query `?- Q.` asks the fundamental question of semantic entailment:
    Does KB |= Q? (Does Q logically follow from the knowledge base?)
Prolog answers this by refutation: it adds the negation of the query `~Q` to the
knowledge base and uses SLD resolution with unification to derive a contradiction
(the empty clause). If a contradiction is reached, the query is proven true and
variable bindings that make it true are returned. If the search tree exhausts without
contradiction, Prolog concludes that the proposition does not follow (returning false).

Question 3:
Why might it be useful to use a Prolog program to verify a plan generated by a
Python program?
Answer:
Using Prolog provides an orthogonal, independent verification paradigm. A Python
planner might contain implementation bugs (e.g., off-by-one errors, mutated global sets,
or flawed heuristic loops). Prolog relies on a proven, decades-old resolution engine
based on mathematical logic. Translating the plan into declarative Prolog queries
allows checking the candidate actions against pure logical facts without sharing any
code, data structures, or runtime bugs with the generator.

Question 4:
What advantage does an independent verifier provide when the original plan was
generated with the help of an LLM?
Answer:
LLMs are statistical sequence predictors that lack formal deductive guarantees. They
are prone to plausible hallucinations—generating plans that sound compelling but violate
underlying domain physics. An independent verifier provides an immutable safety barrier:
it guarantees that no generated action reaches physical actuation unless it has been
formally proven to satisfy all domain invariants. This separation of concerns
("Generative AI for synthesis, Formal Logic for verification") is the bedrock of trustworthy
and robust modern AI engineering.
