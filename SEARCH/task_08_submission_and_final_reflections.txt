PART II: SECTION 6 FINAL REFLECTIONS (ANSWERS 1 - 5)

Question 1:
Why is it important to formulate the search problem before writing the search algorithm?
Answer:
Formulating the search problem as the formal tuple P = (S, A, T, s0, G, c) separates the
mathematical specification of "what the problem is" from the algorithmic implementation
of "how to solve it." By formally defining state granularity, legal actions, transition
rules, and goal criteria before coding, the engineer prevents costly conceptual errors—such
as conflating state with path history, allowing illegal diagonal maneuvers, or incorrectly
evaluating goal achievement. A clear problem formulation provides an unambiguous ground
truth against which both human logic and LLM-generated code can be tested and verified.

Question 2:
In what sense is A* an "informed" search algorithm?
Answer:
A* is an informed (heuristic) search algorithm because its node selection is guided by
problem-specific domain knowledge beyond the edges already traversed. While blind search
algorithms like BFS or Dijkstra only consider the past accumulated cost g(n), A* evaluates
each frontier node using f(n) = g(n) + h(n), where h(n) is an informed estimate of the
remaining distance from n to the goal. This heuristic estimate directs the search frontier
asymmetrically toward the goal, prioritizing promising paths and dramatically reducing the
number of states expanded in unpromising regions of the search space.

Question 3:
Why does the choice of heuristic matter?
Answer:
The heuristic function governs the fundamental trade-off between search speed and solution
optimality. If a heuristic is inadmissible (it overestimates the true cost h*(n)), A*
loses its mathematical guarantee of finding the shortest path and may return a sub-optimal
route. Conversely, if a heuristic is overly pessimistic (such as h(n) = 0), A* degenerates
into blind Uniform Cost Search, wasting computational resources on exhaustive expansion.
Furthermore, as demonstrated in our experiments, a heuristic must match the physical
topology of the domain: Manhattan distance is far more informative than Euclidean distance
for 4-connected grid worlds because it respects the absence of diagonal motion.

Question 4:
What did the LLM contribute to the engineering process?
Answer:
The LLM functioned as an effective software engineering accelerator. It rapidly produced
working Python boilerplate, correctly parsed 2D ASCII strings into structured sets,
implemented the standard min-heap and double-ended queue loops, and generated clear
terminal formatting utilities. This automated the low-level syntactic mechanics of
development, freeing the engineer to focus on higher-level architectural decisions, such
as ensuring goal-checking occurred at expansion rather than generation, preventing heap
comparison bugs, and designing rigorous boundary test cases.

Question 5:
What could go wrong if an engineer simply accepted LLM-generated code without testing it?
Answer:
Blindly accepting LLM-generated code introduces serious risks of silent, catastrophic
failure. LLMs generate code based on statistical pattern matching, which can easily
produce implementations that compile and run cleanly while containing subtle algorithmic
defects. For example, an LLM might check the goal condition when a node is added to the
frontier (breaking A*'s optimality guarantee), fail to break ties safely in priority queues,
or enter an infinite loop when given an unsolvable map. Without systematic empirical
testing across edge cases, an engineer would mistake working syntax for a validated,
sound algorithm.
